## Why

Ostrilo signs Nostr events with keys a user cannot rotate and cannot recover. In that setting, duplicated cryptographic code is a defect in its own right, independent of whether either copy is currently wrong. Two implementations of one primitive drift, a fix lands in the copy nobody calls, and a later refactor rewires the wrong one. For a signer, that failure mode ends with a signature over data the user never saw.

The duplication is already here. `parsePrivateKey` exists three times: `src/domain/utils/crypto.ts:160`, which dispatches to `parsePrivateKeyFromBech32` (line 101) or `parsePrivateKeyFromHex` (line 133); `src/domain/utils/encoding.ts:43`, its own version over `bech32ToBytes` and `hexToBytes`; and `KeyVaultService.parsePrivateKey`, a private method at `src/application/services/key-vault.service.ts:53`. Two of the three are live and they are live on the *same* user flow. The service method is what actually parses an imported key (`key-vault.service.ts:185`), while the `domain/utils/crypto.ts` version is reached through the dynamic import at `src/infrastructure/messaging/handlers/crypto-rpc.ts:62` serving the `crypto.parsePrivateKey` RPC that `ImportKeyForm.tsx:52` and `OnboardingImportKey.tsx:108` call to pre-validate the very input they are about to import. The `encoding.ts` copy has no caller in `src/` at all. So one key-import gesture runs the user's secret through two independently written parsers, and a third parser sits in the tree waiting for someone to import it.

AES-GCM and key derivation are doubled the same way. `src/domain/utils/crypto.ts` carries `deriveKeyFromPassword` (line 178), `encryptPrivateKey` (line 198) and `decryptPrivateKey` (line 256), each hard-coding pure-JS PBKDF2 at 100,000 iterations; `src/infrastructure/crypto/adapters.ts` carries `WebCryptoAesGcm` (line 16) and `NoblePbkdf2` (line 55), and those are what `src/extension/background.ts:3-7` injects into `KeyVaultService`. The `domain/utils/crypto.ts` set has no caller in `src/`, yet it stays exported and importable, which is exactly how a well-intentioned future edit reaches for the wrong one.

Key generation is doubled too, and the two copies already differ. `generatePrivateKey` at `src/domain/utils/crypto.ts:50` uses Noble's `randomBytes(32)`; the live `KeyVaultService.generateKey` at `src/application/services/key-vault.service.ts:135` uses `crypto.getRandomValues(new Uint8Array(32))`. Both are sound CSPRNG sources, so this is not a vulnerability and should not be described as one. It is the drift hazard in its purest form: two functions that mint the user's only irreplaceable secret, differing for no reason anybody recorded.

One of these duplicates is actively harmful. `hexToBytes` in `src/domain/utils/encoding.ts:67-77` validates only that the input length is even. It never checks that the characters are hex, so `parseInt` returns `NaN`, and assigning `NaN` into a `Uint8Array` silently stores `0`. `hexToBytes("zz".repeat(32))` returns 32 zero bytes and throws nothing. It is exported and called directly at `src/ui/state/KeyManagerContext.tsx:112` and `:136` on `key.pubkey`, so a malformed stored pubkey becomes an all-zeros npub in the key list rather than an error. That is silent data corruption where the correctly-guarded paths in the same repo — `parsePrivateKeyFromHex` at `crypto.ts:145`, `HexString32Schema` at `src/infrastructure/validation/schemas.ts:128`, `KeyVaultService.parsePrivateKey` at line 56 — all apply a `^[0-9a-fA-F]{64}$` test before decoding. The existing unit assertion that appears to cover this, `expect(() => hexToBytes("invalid")).toThrow()` (`tests/unit/domain/utils.test.ts:124`), passes only because `"invalid"` has odd length; no test exercises even-length non-hex input.

NIP-01 serialization is the remaining correctness question. `computeEventId` at `src/domain/utils/crypto.ts:385-411` builds the pre-image with `JSON.stringify`. NIP-01 mandates escaping only line break, double quote, backslash, carriage return, tab, backspace and form feed, and states that no other character should be escaped. Measured against that, `JSON.stringify` in this toolchain diverges in two places and agrees in two others. `U+2028`, `U+2029` and `U+007F` pass through raw and unescaped, which matches the spec. Control characters `U+0001` through `U+001F` are escaped as `\u00XX`, which diverges from the spec's letter but matches what most other Nostr implementations do, because they also delegate to their language's JSON serializer. A lone surrogate such as `U+D800` is emitted as `\ud800`, and that is the one genuine interoperability divergence — a hostile page can send one, and a strict verifier will recompute a different id and reject the event. The security-critical property does hold and must be preserved: the extension signs the id it computed, returns that same id, and the approval dialog renders the content faithfully, so the user is never signing something other than what was shown. The exposure is interoperability, not substitution.

Nothing stops any of this from coming back. The project has a clean ports-and-adapters structure and `src/application/ports/crypto.ts` already defines `CryptoAead`, `CryptoKdf` and `Schnorr`, but no rule confines `@noble/*` or `@scure/*` to the adapter layer and no test asserts that a primitive has exactly one implementation. `src/domain/crypto/interfaces.ts` even declares a second, incompatible set of `CryptoAead`, `CryptoKdf`, `Schnorr` and `CryptoService` interfaces that nothing implements; only its `CRYPTO_CONSTANTS` export is used.

## What Changes

- Establish exactly one implementation of each cryptographic primitive, expressed through the ports in `src/application/ports/crypto.ts`, and delete every duplicate after proving it has no live caller.
- **BREAKING** (internal module surface, no user-visible behaviour): remove the dead export surface of `src/domain/utils/crypto.ts` — `generatePrivateKey`, `getPublicKey`, `generateKeyPair`, `privateKeyToBech32`, `publicKeyToBech32`, `publicKeyToHex`, `parsePrivateKeyFromBech32`, `parsePrivateKeyFromHex`, `deriveKeyFromPassword`, `encryptPrivateKey`, `decryptPrivateKey`, `signHash`, `createHash`, `verifySignature`, `isWebAuthnAvailable`, `isPlatformAuthenticatorAvailable` — and the unused duplicate interfaces in `src/domain/crypto/interfaces.ts`.
- Collapse the three `parsePrivateKey` implementations to one, reached by both the `crypto.parsePrivateKey` RPC handler and `KeyVaultService.importKey`.
- Split the NIP-01 pre-image from the hash: a pure domain serializer that produces the `[0, pubkey, created_at, kind, tags, content]` string with no library dependency, and a hashing adapter behind a port.
- Harden the hex codec so non-hex input throws instead of silently decoding to zero bytes, then audit and fix every caller that currently depends on the silent-zero behaviour.
- Reject content containing lone surrogates at the `UnsignedEventSchema` validation boundary so unpaired code units can never reach `computeEventId`, and keep `JSON.stringify` as the serializer rather than hand-rolling NIP-01 escaping.
- Replace the deprecated `String.prototype.substr` calls (`src/domain/utils/crypto.ts:151`, `:427`, `:456`, `:461`, `:466`; `src/domain/utils/encoding.ts:74`) with the hardened codec.
- Add enforcement so the duplication cannot return: an ESLint `no-restricted-imports` rule confining `@noble/*` and `@scure/*` to `src/infrastructure/`, and a test asserting there is exactly one implementation of each primitive.

This change is behaviour-preserving by construction. No new algorithm, no storage-format change, no KDF parameter change, and no change to the meaning of any RPC method ship here. Confining `@scure/base` to the adapter layer does require one additive field on the key-list response so the UI stops encoding bech32 itself, and a malformed stored pubkey stops rendering as a zero-derived npub and starts surfacing as an error. Those are the only two user-observable movements. Argon2id, iteration counts, AAD binding and the versioned vault record belong to `harden-vault-key-derivation`; removing the raw-secret response from `crypto.parsePrivateKey` belongs to `remove-key-exfiltration-surface`.

## Capabilities

### New Capabilities

- `crypto-primitives`: One canonical implementation of each cryptographic primitive, reached only through the application ports; a hex codec that rejects malformed input loudly; and a layer boundary that keeps cryptographic libraries out of the domain, application and UI layers.

### Modified Capabilities

- `nip07-provider`: `Event ID Computation` gains an explicit statement of which characters the NIP-01 pre-image escapes, and the requirement that events whose content or tags contain unpaired surrogate code units are rejected before an id is computed.

## Impact

- Domain: `src/domain/utils/crypto.ts` shrinks to the primitives that are genuinely pure and genuinely used; the NIP-01 pre-image serializer and the hardened hex codec become their own domain modules. `src/domain/utils/encoding.ts` loses its duplicate `parsePrivateKey` and its unsafe `hexToBytes`. `src/domain/crypto/interfaces.ts` retains only `CRYPTO_CONSTANTS`, which `src/domain/utils/validation.ts:6` and `src/domain/utils/encoding.ts:7` import.
- Ports: `src/application/ports/crypto.ts` needs a hashing port and a bech32 port so `computeEventId` and `parsePrivateKey` can stop importing `@noble/hashes` and `@scure/base` from inside the hexagon.
- Adapters: `src/infrastructure/crypto/adapters.ts` becomes the single home for every `@noble/*` and `@scure/*` call, adding SHA-256 and bech32 adapters beside `WebCryptoAesGcm`, `NoblePbkdf2` and `NobleSchnorr`.
- Application service: `KeyVaultService` drops its private `parsePrivateKey`, `toHex` (line 47) and the ad hoc hex decode in `sign` (line 395-397) in favour of the shared codec, and takes the new ports by constructor injection. It imports `@noble/hashes/utils.js` (line 8) and `@scure/base` (line 9) directly today; both move behind ports.
- RPC handlers: `src/infrastructure/messaging/handlers/crypto-rpc.ts:62` must resolve to the single parser. `src/infrastructure/messaging/handlers/nostr-rpc.ts:16-17` imports `signEventHash` and `publicKeyToHex` and never uses either; both imports go.
- Validation: `UnsignedEventSchema` in `src/infrastructure/validation/schemas.ts:140-146` gains a well-formed-string check on `content` and `tags`, returning the existing `invalid_event` code.
- UI: `src/ui/state/KeyManagerContext.tsx:112` and `:136` must handle a hex codec that now throws, instead of silently rendering an npub derived from zero bytes. `src/ui/features/profile/components/ProfileView.tsx:4` imports `hexToNpub`, which must move to the surviving bech32 path.
- Build tooling: ESLint is not currently installed or configured in this repo, so the `no-restricted-imports` guard arrives with the linter itself. `knip.json` exists without `knip` as a devDependency, so the dead-export proof needs either that dependency added or an equivalent grep gate.
- Tests: `tests/unit/domain/utils.test.ts` and `tests/unit/domain/domain-utils.test.ts` are 255-line near-duplicates covering the same modules and differing in five assertions; they collapse to one file. `tests/test-crypto.ts`, `tests/security/memory-zeroization.test.ts`, `tests/unit/domain/nostr-events.test.ts`, `tests/unit/infrastructure/rpc-handlers.test.ts` and `tests/unit/infrastructure/rpc-validation.test.ts` all reference symbols this change removes or relocates.
- Sequencing: `restore-security-test-assurance` supplies the BIP-340 and NIP-01 known-answer vectors that make this refactor provable rather than merely plausible, and `harden-vault-key-derivation` rewrites the live KDF, AES-GCM usage and vault record format in the same files. Both should land first; see `design.md` for the ordering rationale.
