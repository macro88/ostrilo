## Why

Roadmap requirement SEC-009 (`docs/roadmap.md`) asks for WebAuthn biometric unlock "as an alternative or supplement to password-based unlock". Today there is exactly one credential-to-KEK producer in the product: `openEnvelope` (`src/application/services/key-vault.service.ts:183-207`), which runs Argon2id at `m=19456, t=2, p=1` — 611 ms in the MV3 service worker, measured in `openspec/changes/archive/2026-09-17-harden-vault-key-derivation/kdf-measurements.md` — against a long master password typed into the popup lock screen many times a day. That is the highest-frequency secret exposure Ostrilo has, and it is the one the product has no defence for: a password observed once by a shoulder, a camera, a keylogger or a malicious IME is full authority over a Nostr identity forever.

Every vault change so far has deliberately fenced this off rather than solved it. `harden-vault-key-derivation` lists "No WebAuthn, biometric, or hardware-backed unlock" in its Non-Goals (`openspec/changes/archive/2026-09-17-harden-vault-key-derivation/design.md:32`); `implement-session-auto-lock` does the same. `grep -i biometric openspec/specs/` returns nothing. This change is the named owner of that ground.

It starts from below zero, not from a stub. Two controls that claimed this feature were deleted for lying: a biometric-unlock checkbox bound to local state whose handler reported the feature did not work (`src/ui/features/settings/components/SecuritySettingsTab.tsx:16-22` — "A control that cannot do anything is a promise the surface cannot keep"), and a lock-screen biometric button "whose only behaviour was to report that it did not work" (`src/ui/features/authentication/components/LockScreen.tsx:70-77`). The WebAuthn capability helpers were removed as dead code by `consolidate-crypto-implementations` (`openspec/changes/archive/2026-09-17-consolidate-crypto-implementations/tasks.md:76`). Nothing in `src/` calls `navigator.credentials` today.

The vault already has the shape this needs. One password-derived KEK wraps per-record DEKs (`key-vault.service.ts:78-86`), and a known-plaintext verifier sealed under that KEK (`:44`, `:191-199`) proves any candidate KEK before per-record work. A second, WebAuthn-PRF-wrapped copy of **the same KEK** is additive: no new KEK, no envelope version bump, no ciphertext re-encrypted.

What this change is not: a replacement for the password. A PRF secret has no escrow. It dies with the credential, with the Secure Enclave, with a Hello PIN reset, and with the extension ID. The password therefore stays enrolled, sufficient and non-removable, and "biometric only" is never an offerable state. It is also not an anti-malware control — code running in the user's session can open the ceremony window and prompt the user itself — and the enable-time copy says so rather than implying otherwise.

## What Changes

- Add a `biometric-unlock` capability: a second AES-GCM wrapping of the existing vault KEK, opened by a WebAuthn PRF output, and admitted only after **two independent gates**.
  - **Gate A (possession of the secret):** the PRF output is stretched with HKDF-SHA256 into a non-extractable wrapping key that decrypts the stored copy of the KEK, which must then decrypt the envelope verifier.
  - **Gate B (proof of a live ceremony):** the background mints a single-use 32-byte challenge, consumes it on read before any verification, and verifies the ECDSA P-256 assertion signature itself. A captured PRF output alone unlocks nothing.
- Add `browser.storage.local["vaultBiometric"]`, one factor record. Not a field on `vaultEnvelope` — `verifierAad` covers `envelope.v`, so a bump would force re-encrypting the verifier, which needs the password — and not in `storage.sync`, so a device-bound credential never replicates across profiles.
- Add a fourth AAD domain `ostrilo/vault-bio-wrap` to `src/domain/crypto/aad.ts`, which has exactly three today (`:27-31`). It binds the envelope version, every KDF cost field and the envelope salt via the existing `kdfFields` helper, plus the credential id, the **observed** rpIdHash and origin, the credential public key, the algorithm, the backup-eligible bit, the PRF salt and the HKDF info version. Every field the verifier consults is inside the AEAD tag, so a storage writer cannot substitute a public key it controls or flip the sync-policy bit.
- Add `CryptoHkdf` to `src/application/ports/crypto.ts` with a `VaultHkdf` adapter over `crypto.subtle`. It returns a **non-extractable `CryptoKey`** and never derived bytes, because `src/domain/utils/memory.ts:10-21` cannot zeroize a `CryptoKey`.
- Add an `EcdsaP256` verify-only port and a `NobleEcdsaP256` adapter. `@noble/curves@^2.2.0` is already a dependency (`package.json:48`), so no new package.
- Add a `WebAuthnCeremony` port (`src/application/ports/webauthn.ts`) and a Window-only adapter. Enrolment is `create()` then an immediate `get()`; `prf.enabled` is never treated as proof of delivery. The background never imports it.
- Add three small pure parsers under `src/domain/webauthn/` for `authenticatorData`, `clientDataJSON` and an SPKI P-256 public key. **No CBOR decoder**: `attestationObject` is never read, `attestation: "none"` is requested, and `pubKeyCredParams` is `[-7]` only, so there is no RSA path and no COSE algorithm-confusion surface.
- Add `BiometricFactorService` (`src/application/services/biometric-factor.service.ts`), the only writer of `vaultBiometric` and the only reader of the challenge, exposing `kekFromFactor()` as a sibling producer to `openEnvelope`.
- Add a dedicated `unlock.html` entrypoint opened with `browser.windows.create`. Chrome refuses WebAuthn on a non-visible `WebContents`, which rules out offscreen documents and hidden frames; the action popup is ruled out by Bitwarden's own fix for this exact problem (`bitwarden/clients#4695`, "Open WebAuthn Prompt in New Tab for all browser extensions") and by Firefox bug 2026687. No new permission — `windows` is already in the reviewed set (`wxt.config.ts:139`).
- Add six RPC methods to the existing UI-only `vault` namespace: `biometricStatus`, `biometricBeginUnlock`, `biometricCompleteUnlock`, `biometricForget` (locked-reachable) and `biometricBeginEnroll`, `biometricEnroll` (lock-gated). Add `BIOMETRIC_UNAVAILABLE` (-32007) and `BIOMETRIC_REJECTED` (-32008); both numeric slots are free (`src/infrastructure/messaging/error-codes.ts:124-148`). Every ceremony, challenge, signature, flag and unwrap failure collapses to the refusal code with one fixed detail, so the response is never an oracle.
- Add `authFactor: "password" | "biometric"` to the session `LockState` (`key-vault.service.ts:46-50`). A biometric session holds **reduced authority**: backup, key add or import, delete, the two re-auth-gated settings, the three password-gated policy cases and enrolling a factor all keep `requireReauth(password, …)` (`src/infrastructure/messaging/reauth.ts:31-58`), and `vault.reveal` verifies the password inline (`vault-rpc.ts:356-383`), so every one of them refuses a biometric session by construction. The boundary is exactly the existing password-gated set and no wider — see `design.md` Decision 7.
- Add a background-enforced 30-day password rehearsal and a **first-unlock-after-restart** rule: the first unlock of a browser session is password-only. Both blunt the availability risk of a factor the user stops rehearsing, and the restart rule also blunts the physical-access and coercion cases that biometrics otherwise make worse.
- **BREAKING** (in-memory behaviour, no stored format change): fix the unzeroized `this.unlocked.clear()` at `key-vault.service.ts:611`, which `lock()` does correctly at `:765-767`. A second unlock entry point makes a re-entrant unlock materially more likely, so this stops being a drive-by.
- **BREAKING** (shared security constant): make `KEY_HANDLING_DOCUMENTS` (`src/infrastructure/messaging/key-handling-documents.ts`) target-aware. `tests/security/key-handling-bundle.test.ts:113` does an unguarded `readFileSync` for **both** `.output/chrome-mv3` and `.output/firefox-mv3`, so a Chromium-only document would crash `pnpm run test:build-output` with ENOENT instead of failing an assertion.
- Gate the feature out of the Firefox build at compile time via `src/domain/platform/build-target.ts` exporting `IS_CHROMIUM_BUILD` from `import.meta.env.BROWSER`, plus a WXT per-entrypoint target filter for `unlock.html`. The feature is **absent**, not a disabled control — the precedent `SecuritySettingsTab.tsx:16-22` sets explicitly.
- Add the lock-screen ghost affordance and the Security-tab section, both with designed states for: no usable factor, cancelled, refused, rate-limited, rehearsal due, restart-pending, and permanently unusable.

Not in this change: biometric re-authentication, biometric reveal, biometric key add or import, multiple enrolled credentials, an onboarding enrolment step, a settings-sync flag, `largeBlob`, attestation verification, Firefox, and Safari.

### Kill criterion

Task group 1 is a measurement spike, following the `kdf-measurements.md` precedent of measuring before committing to a parameter. It is written into the proposal so a reviewer can hold the work to it rather than rationalising whatever the spike returns:

- **If no authenticator class returns 32 PRF bytes for a `chrome-extension://<id>` relying-party identifier on any target platform**, this change is withdrawn. It is not narrowed, and the owned-HTTPS-domain route is re-opened as a different change with its own argument about `host_permissions`.
- **If PRF works on Windows and Linux but no macOS platform authenticator answers**, the change ships narrowed as security-key-first, and the SEC-009 row in `docs/roadmap.md` is rewritten to drop "fingerprint, Face ID" for the honest matrix in the same change.
- **If no ceremony host satisfies Chrome's visible-`WebContents` requirement**, the change is withdrawn; there is no remaining surface to run it in.

## Capabilities

### New Capabilities

- `biometric-unlock`: a second, PRF-wrapped copy of the vault KEK admitted only by both a wrapped-key gate and a background-verified live assertion; enrolment that proves a full PRF round trip before persisting anything; a relying-party identity recorded as observed rather than computed; reduced session authority; password rehearsal and first-unlock-after-restart; single-code failure reporting; and compile-time absence from non-Chromium builds.

### Modified Capabilities

- `key-vault`: "Zero-Retention Password Handling" admits exactly two KEK producers, both proving the recovered key against the verifier before per-record work; "Memory Zeroization" extends to the PRF output and its decoded buffer, and states plainly what cannot be zeroized; unlock repopulates key material before reporting unlocked, and zeroizes previously held keys before clearing the map.
- `vault-key-derivation`: a biometric wrapping is not a KDF algorithm variant and must not pass `assertKdfAcceptable`; the envelope version is not bumped and the verifier is not re-encrypted; the wrapping binds the live envelope's parameters so a rolled-back envelope makes it undecryptable by construction.
- `crypto-primitives`: HKDF-SHA256 and ECDSA P-256 verification each reached through a port with one adapter; the HKDF port returns a non-extractable key and never bytes; WebAuthn ceremony access is a separate Window-only port the background must not import.
- `unlock-throttling`: the biometric path shares the single global failure counter, checks it before minting or consuming a challenge, and records a failure on any background verification failure — but never on a user cancellation, which never reaches the background.
- `session-auto-lock`: the four status and unlock methods stay locked-reachable and the two enrolment methods stay privileged; the session record names the factor that opened it; a biometric session is subject to the same auto-lock deadline and the same fail-closed reads.
- `rpc-privilege-boundary`: biometric methods are not page-reachable; a PRF output may travel from a document to the background and never in reverse. Also **corrects** the existing requirement at `openspec/specs/rpc-privilege-boundary/spec.md:37`, which requires `sender.tab` to be absent — the implementation deliberately does not (`src/infrastructure/messaging/rpc-router.ts:72-77`: "Requiring its absence would break them"), because the options page opens in a tab and the approval page is a created window. The ceremony window is a third such sender.
- `key-material-isolation`: the named set that must not cross the realm boundary or be staged in storage extends to the vault KEK, any wrapping key, and any PRF output.
- `rpc-error-codes`: two codes added with the four-edit protocol; every biometric failure collapses to the single refusal code.
- `extension-manifest-policy`: the reviewed permission set stays exactly `storage`, `windows`, `alarms`; no host permission is declared, **including for a relying-party identifier**; the ceremony page is an enumerated, non-web-accessible extension page present in the Chromium build only. (The pinned Chromium manifest `key` is owned by the prerequisite `pin-extension-id` change, not by this one.)
- `build-output-integrity`: the key-handling document list is expressed per build target, and a target-scoped document is asserted absent from the others rather than read unconditionally.
- `ui-security`: the ceremony page is a key-handling document holding the PRF output only in a ref; the lock screen keeps one notched primary; enable-time disclosure is part of the surface and never names a biometric modality.
- `ui-options-page`: the Security tab renders the section only after a live capability round trip, an explanatory non-interactive row when it fails, and nothing at all where the feature is not compiled in.
- `unlock-feedback`: distinct designed states for every biometric outcome, each naming the password as the working alternative.

## Impact

- **Prerequisite change, must land and be published first:** `pin-extension-id`. The relying-party identifier is literally `chrome-extension://<id>`, and `wxt.config.ts` declares no manifest `key` — dev, CI, unpacked and Web Store builds have four different IDs and therefore four different RP IDs, so every enrolled credential would be invalidated at publish. `key` is Chrome-only and `wxt.config.ts` builds one manifest via `manifest: (env) => ({…})`, so it must sit behind an `env.browser === "firefox" ? {} : { key }` branch exactly as `use_dynamic_url` already does (`wxt.config.ts:155`), or an unknown top-level key ships to AMO. The key is read off the existing Chrome Web Store listing.
- **In-flight collision:** `openspec/changes/add-auto-lock-countdown` targets the same `SecuritySettingsTab`, the same `session-auto-lock` spec and the same `ui-options-page` spec. One must rebase, and its `lockAt` disclosure and this change's `biometricStatus` want their lock-gate classification decided in one pass.
- Domain: `src/domain/types.ts` (factor types, `authFactor` on the lock state, rehearsal constant), `src/domain/crypto/aad.ts` (fourth domain), new `src/domain/webauthn/`, new `src/domain/platform/build-target.ts`.
- Application: `src/application/ports/crypto.ts` (HKDF, ECDSA), new `src/application/ports/webauthn.ts`, new `biometric-factor.service.ts`, and `key-vault.service.ts` (`openVaultWithKek` extraction at `:611-665`, `unlockWithFactor`, the `:611` zeroization fix, `lastPasswordUnlockAt`).
- Infrastructure: `adapters.ts` (HKDF, ECDSA), new `src/infrastructure/webauthn/`, `rpc.ts`, `vault-rpc.ts`, `schemas.ts`, `error-codes.ts`, `client.ts`, and `rpc-router.ts` (`LOCKED_REACHABLE_METHODS`).
- Extension: new `src/extension/unlock/`, and `wxt.config.ts` for the per-target entrypoint filter.
- UI: `LockScreen`, `KeyManagerContext` (`UnlockResult`, `UNLOCK_FAILURE_COPY`), `SecuritySettingsTab`, `ReauthDialog`, and `key-handling-documents.ts`.
- Tests: four new security suites, a Playwright CDP virtual-authenticator fixture (`tests/e2e/fixtures/` has no CDP usage today), and edits to `tests/security/key-handling-bundle.test.ts` and `tests/security/manifest-assertions.test.ts`.
- Docs: `docs/vault-storage-format.md`, `docs/rpc-architecture.md`, `docs/rpc-error-codes.md`, `docs/design-review/`, and the SEC-009 row in `docs/roadmap.md`.
