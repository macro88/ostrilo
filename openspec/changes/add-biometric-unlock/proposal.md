## Why

Roadmap requirement SEC-009 (`docs/roadmap.md`) asks for WebAuthn biometric unlock. Today there is exactly one credential-to-KEK producer in the product: `openEnvelope` in `src/application/services/key-vault.service.ts`, which runs Argon2id at `m=19456, t=2, p=1` — 611 ms in the MV3 service worker, measured in `openspec/changes/archive/2026-09-17-harden-vault-key-derivation/kdf-measurements.md` — against a long master password. Auto-lock is bounded at 60 minutes and defaults to 5 (`AUTO_LOCK_BOUNDS` in `src/domain/types.ts`), so that password is typed into the lock screen many times a day. It is the highest-frequency secret exposure Ostrilo has, and the largest daily friction: a password observed once by a shoulder, a camera, a keylogger or a malicious IME is full authority over a Nostr identity forever.

Every vault change so far has deliberately fenced this off rather than solved it. `harden-vault-key-derivation` lists "No WebAuthn, biometric, or hardware-backed unlock" in its Non-Goals; `implement-session-auto-lock` does the same. `keep-unlocked-session-alive` made the configured timeout real but did not lengthen it. This change is the named owner of the ground they left.

It starts from below zero, not from a stub. Two controls that claimed this feature were deleted for lying: a biometric-unlock checkbox in `SecuritySettingsTab.tsx` bound to local state, and a lock-screen biometric button in `LockScreen.tsx` "whose only behaviour was to report that it did not work". Both files still carry the comment recording why. The WebAuthn capability helpers were removed as dead code by `consolidate-crypto-implementations`. Nothing in `src/` calls `navigator.credentials` today.

The vault already has the shape this needs. One password-derived KEK wraps per-record DEKs, and a known-plaintext verifier sealed under that KEK proves any candidate KEK before per-record work. A second, WebAuthn-PRF-wrapped copy of **the same KEK** is additive: no new KEK, no envelope version bump, no ciphertext re-encrypted.

What this change is not: a replacement for the password. A PRF secret has no escrow. It dies with the credential, with a passkey deleted from the provider, with a Hello PIN reset, and with the extension ID. The password therefore stays enrolled, sufficient and non-removable, and "biometric only" is never an offerable state. It is also not an anti-malware control — code running in the user's session can prompt the user itself, and a PRF output it captures is as good as the key — and the enable-time copy says so rather than implying otherwise.

## What Changes

- Add a `biometric-unlock` capability: a second AES-GCM wrapping of the existing vault KEK, opened by a WebAuthn PRF output. The PRF output is stretched with HKDF-SHA256 into a non-extractable wrapping key that decrypts the stored copy of the KEK, which must then decrypt the envelope verifier. That decryption is the only admission gate.
- **No background-verified assertion.** An earlier draft added a second gate: a single-use challenge and an ECDSA P-256 signature check in the background, so that "a captured PRF output alone unlocks nothing". The claim does not hold. The PRF output is static, and every input to the wrapping's AAD is stored in plaintext, so anyone holding a PRF output and a copy of `storage.local` recovers the KEK offline without the background — and every party in a position to capture a PRF output (an extension page, local malware) can also read `storage.local`. The gate is removed, with its challenge store, its ECDSA port and its three wire parsers, and the specs state what a captured output is worth instead. See `design.md` Decision 3.
- Add `browser.storage.local["vaultBiometric"]`, one factor record. Not a field on `vaultEnvelope` — `verifierAad` covers `envelope.v`, so a bump would force re-encrypting the verifier, which needs the password — and not in `storage.sync`, so the record never replicates across profiles.
- Add a fourth AAD domain `ostrilo/vault-bio-wrap` to `src/domain/crypto/aad.ts`, which has exactly three today. It binds the envelope version, every KDF cost field and the envelope salt via the existing `kdfFields` helper, plus the wrapper version, the credential id, the PRF salt, the HKDF info version and the backup-eligible flag.
- Add `CryptoHkdf` to `src/application/ports/crypto.ts` with a `VaultHkdf` adapter over `crypto.subtle`. It returns a **non-extractable `CryptoKey`** and never derived bytes, because `src/domain/utils/memory.ts` cannot zeroize a `CryptoKey`. The AEAD adapter already runs on `crypto.subtle`, so this adds no second AES-GCM implementation.
- Add a `WebAuthnCeremony` port (`src/application/ports/webauthn.ts`) and one Window-only adapter module. Enrolment is `create()` then an immediate `get()`; `prf.enabled` is never treated as proof of delivery. The background never imports it.
- Add `BiometricFactorService` (`src/application/services/biometric-factor.service.ts`), the only reader and writer of `vaultBiometric`, exposing `kekFromFactor()` as a sibling producer to `openEnvelope`.
- **Unlock** runs in a dedicated `unlock.html` entrypoint opened with `browser.windows.create`. Chrome refuses WebAuthn on a non-visible `WebContents`, which rules out offscreen documents and hidden frames; the action popup closes when it loses focus to the authenticator prompt, which is why Bitwarden moved its ceremony out (`bitwarden/clients#4695`). No new permission — `windows` is already in the reviewed set.
- **Enrolment** runs in the options page, in the tab whose `ReauthDialog` collected the password. Enrolment needs the password and the PRF output in one operation, the specs forbid either crossing between documents, and the background must not hold a KEK while it waits for a ceremony. The only arrangement that satisfies all three is to run the ceremony where the password already is.
- Add five RPC methods to the existing UI-only `vault` namespace: `biometricStatus`, `biometricUnlockRequest`, `biometricUnlock`, `biometricForget` (locked-reachable) and `biometricEnroll` (lock-gated). Add `BIOMETRIC_UNAVAILABLE` (-32007) and `BIOMETRIC_REJECTED` (-32008); both numeric slots are free in `error-codes.ts`. Every unlock and enrolment refusal collapses to the refusal code with one fixed detail.
- Add `authFactor: "password" | "biometric"` to the session `LockState`. A biometric unlock **never stands in for the password**: `vault.reveal`, `vault.generate`, `vault.import`, `vault.deleteKey`, `vault.changePassword`, the two `REAUTH_SETTINGS_FIELDS` timeouts and the three policy cases that call `requireReauth` all ask for the password in every session, so none of them can be satisfied by a ceremony, with no new enforcement code. This is not a reduced tier — a password-opened session is asked for the password by the same operations — and no surface calls it one.
- Add a background-enforced 30-day password rehearsal and a **first-unlock-after-restart** rule: the first unlock of a browser session is password-only. Both blunt the availability risk of a factor the user stops rehearsing, and the restart rule also blunts the physical-access and coercion cases.
- Refuse biometric unlock while a password-change journal (`vaultRotation`) is present, and while any record is unversioned. `recoverInterruptedRotation` chooses between two journalled states by trying the password against each; a factor has no password to try. The lock screen says the password is needed this time.
- Delete the factor on every envelope write, at `saveEnvelope`, before the envelope is written. That covers envelope creation, `commitRotation` and both branches of `recoverInterruptedRotation`, so a password change can never leave a wrapping that opens a KEK the user believes they rotated away from.
- **BREAKING** (shared security constant): make `KEY_HANDLING_DOCUMENTS` (`src/infrastructure/messaging/key-handling-documents.ts`) target-aware. `tests/security/key-handling-bundle.test.ts` does an unguarded `readFileSync` of every listed document for **both** `.output/chrome-mv3` and `.output/firefox-mv3`, so a Chromium-only document would crash `pnpm run test:build-output` with ENOENT instead of failing an assertion.
- Gate the feature out of the Firefox build at compile time via `src/domain/platform/build-target.ts` exporting `IS_CHROMIUM_BUILD` from `import.meta.env.BROWSER`, plus a WXT per-entrypoint target filter for `unlock.html`. The feature is **absent**, not a disabled control.
- Add the lock-screen ghost affordance and the Security-tab section, both with designed states for: no usable factor, cancelled, refused, rate-limited, rehearsal due, restart-pending, password needed once, permanently unusable, and — at enrolment — an authenticator that returned no PRF output.

Not in this change: assertion verification, biometric re-authentication, biometric reveal, biometric key add or import, multiple enrolled credentials, an onboarding enrolment step, a settings-sync flag, `largeBlob`, attestation, Firefox, and Safari.

### Kill criterion

Task group 1 is a measurement spike, following the `kdf-measurements.md` precedent of measuring before committing to a parameter. It is written into the proposal so a reviewer can hold the work to it rather than rationalising whatever the spike returns:

- **If no authenticator class returns 32 PRF bytes for a `chrome-extension://<id>` relying-party identifier on any target platform**, this change is withdrawn. It is not narrowed, and the owned-HTTPS-domain route is re-opened as a different change with its own argument about `host_permissions`.
- **If no macOS platform authenticator answers**, the change ships narrowed as security-key-first, and the SEC-009 row in `docs/roadmap.md` is rewritten for the honest matrix in the same change.
- **If the only macOS authenticators that answer are synced passkey providers** — the expected result, see `design.md` Context — the change ships, and the synced-credential disclosure moves from a caveat to the first statement in the enable-time copy on that platform.
- **If any authenticator class returns the enrolled PRF output to a presence-only ceremony**, that class is not offered. With no assertion check in the background, the authenticator binding its output to user verification is the only thing that makes "biometric" true.
- **If no ceremony host satisfies Chrome's visible-`WebContents` requirement**, the change is withdrawn. If the created window qualifies and a foreground options tab does not, enrolment moves into the created window, which then collects the password itself; that is a redesign of group 11, decided before it starts.

## Capabilities

### New Capabilities

- `biometric-unlock`: a second, PRF-wrapped copy of the vault KEK whose only admission gate is that the authenticator's output opens it; an honest statement of what a captured output is worth; enrolment that proves a full PRF round trip before persisting anything and runs in the document that holds the password; user verification measured per authenticator class rather than assumed; a biometric unlock that never stands in for the password; password rehearsal and first-unlock-after-restart; refusal while a legacy record or an unfinished password change needs the password; single-code failure reporting; and compile-time absence from non-Chromium builds.

### Modified Capabilities

- `key-vault`: "Zero-Retention Password Handling" admits exactly two KEK producers, both proving the recovered key against the verifier before per-record work; "Memory Zeroization" extends to the PRF output and its decoded buffer, and states plainly what cannot be zeroized; unlock repopulates key material before reporting unlocked.
- `vault-key-derivation`: a biometric wrapping is not a KDF algorithm variant and must not pass `assertKdfAcceptable`; the envelope version is not bumped and the verifier is not re-encrypted; the wrapping binds the live envelope's parameters so a rolled-back envelope makes it undecryptable by construction.
- `crypto-primitives`: HKDF-SHA256 reached through a port with one adapter, returning a non-extractable key and never bytes; no new asymmetric verification; WebAuthn ceremony access is a separate Window-only port the background must not import.
- `unlock-throttling`: the biometric path shares the single global failure counter, checks it before reading the factor, and records a failure when a supplied output fails to open the wrapping — but never on a user cancellation, and never on a refusal that only says the password is needed.
- `session-auto-lock`: the four status and unlock methods stay locked-reachable and enrolment stays privileged; the session record names the factor that opened it; a biometric session is subject to the same auto-lock deadline and the same fail-closed reads. Rebased onto the lock-reason disclosure `keep-unlocked-session-alive` added.
- `rpc-privilege-boundary`: biometric methods are not page-reachable; a PRF output may travel from a document to the background and never in reverse. Also **corrects** the existing requirement that `sender.tab` be absent — the implementation deliberately does not require it, because the options page opens in a tab and the approval page is a created window. The ceremony window is a third such sender.
- `key-material-isolation`: the named set that must not cross the realm boundary or be staged in storage extends to the vault KEK, any wrapping key, and any PRF output; enrolment keeps the password and the output in one document.
- `rpc-error-codes`: two codes added with the four-edit protocol; every biometric refusal collapses to the single refusal code; enrolment state is disclosed by the status method and by nothing else.
- `extension-manifest-policy`: the reviewed permission set stays exactly `storage`, `windows`, `alarms`, `idle`; no host permission is declared, **including for a relying-party identifier**; the ceremony page is an enumerated, non-web-accessible extension page present in the Chromium build only. (The pinned Chromium manifest `key` is owned by the prerequisite `pin-extension-id` change, not by this one.)
- `build-output-integrity`: the key-handling document list is expressed per build target, and a target-scoped document is asserted absent from the others rather than read unconditionally.
- `ui-security`: the ceremony page is a key-handling document holding the PRF output only in a ref, and the options page holds the enrolment output on the same terms; the lock screen keeps one notched primary; enable-time disclosure is part of the surface and never names a biometric modality.
- `ui-options-page`: the Security tab renders the section only after a live capability round trip, an explanatory non-interactive row when it fails, and nothing at all where the feature is not compiled in; it runs the enrolment ceremony itself and has a designed state for an authenticator that returns no output. Rebased onto the countdown `add-auto-lock-countdown` added.
- `unlock-feedback`: distinct designed states for every biometric outcome, each naming the password as the working alternative.

## Impact

- **Prerequisite change, must land and be published first:** `pin-extension-id`, which does not exist yet. The relying-party identifier is literally `chrome-extension://<id>`, and `wxt.config.ts` declares no manifest `key` — dev, CI, unpacked and Web Store builds have different IDs and therefore different RP IDs, so every enrolled credential would be invalidated at publish. `key` is Chrome-only and `wxt.config.ts` builds one manifest via `manifest: (env) => ({…})`, so it must sit behind an `env.browser === "firefox" ? {} : { key }` branch exactly as `use_dynamic_url` already does, or an unknown top-level key ships to AMO. The key is read off the Chrome Web Store listing.
- Domain: `src/domain/types.ts` (factor types, rehearsal constant), `src/domain/crypto/aad.ts` (fourth domain), new `src/domain/platform/build-target.ts`.
- Application: `src/application/ports/crypto.ts` (HKDF), new `src/application/ports/webauthn.ts`, new `biometric-factor.service.ts`, and `key-vault.service.ts` (an `openVaultWithKek` extraction from `unlockNow`, `unlockWithFactor`, `authFactor` on `LockState`, the factor deletion in `saveEnvelope`, `lastPasswordUnlockAt`).
- Infrastructure: `crypto/adapters.ts` (HKDF), new `src/infrastructure/webauthn/`, `messaging/rpc.ts`, `messaging/handlers/vault-rpc.ts`, the validation schemas, `messaging/error-codes.ts`, `messaging/client.ts`, and `messaging/rpc-router.ts` (`LOCKED_REACHABLE_METHODS`).
- Extension: new `src/extension/unlock/`, and `wxt.config.ts` for the per-target entrypoint filter.
- UI: `LockScreen`, `KeyManagerContext`, `SecuritySettingsTab` (which now runs the enrolment ceremony), `ReauthDialog`, `ChangePasswordDialog` (re-enrol line), and `key-handling-documents.ts`.
- Tests: three new security suites, a Playwright CDP virtual-authenticator fixture, and edits to `tests/security/key-handling-bundle.test.ts`, `tests/security/manifest-assertions.test.ts` and `tests/security/lock-gate.test.ts`.
- Docs: `docs/vault-storage-format.md`, `docs/rpc-architecture.md`, `docs/rpc-error-codes.md`, `docs/design-review/`, and the SEC-009 row in `docs/roadmap.md`.
