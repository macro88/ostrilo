## Context

Ostrilo's manifests are generated by WXT 0.20.26 from `wxt.config.ts` plus the entrypoints in `src/extension/`. Nobody has audited the result. Reading the two committed build outputs shows five distinct problems.

**No content security policy is declared.** Neither `.output/chrome-mv3/manifest.json` nor `.output/firefox-mv2/manifest.json` contains a `content_security_policy` key. WXT does not add one on production builds: `addDevModeCsp` in `node_modules/wxt/dist/core/utils/manifest.mjs:234` is the only writer, and it only appends a `script-src` source when `wxt.config.command === "serve"`. MV3's platform default already blocks remote script and `eval`, so this is not an immediately exploitable hole, but nothing pins that guarantee and nothing at all restricts where extension pages may connect or fetch media. A signer should declare its own policy rather than inherit one.

**The Firefox manifest is invalid.** `sidebar_action` in `.output/firefox-mv2/manifest.json` reads:

```json
"sidebar_action": {
  "default_panel": "sidepanel.html",
  "browser_style": "true|false",
  "default_icon": "{\n        16: '/icon-16.png',\n        24: '/icon-24.png',\n        ...\n      }",
  "default_title": "Default Side Panel Title",
  "open_at_install": "true|false"
}
```

`browser_style` and `open_at_install` are the literal string `"true|false"` where booleans belong, and `default_icon` is a JavaScript object literal serialised as a string, complete with an ellipsis. The root cause is not `wxt.config.ts`. `src/extension/sidepanel/index.html` still carries WXT's scaffold block verbatim:

```html
<title>Default Side Panel Title</title>
<meta name="manifest.default_icon" content="{ 16: '/icon-16.png', ... }" />
<meta name="manifest.open_at_install" content="true|false" />
<meta name="manifest.browser_style" content="true|false" />
```

WXT reads `manifest.*` meta tags as entrypoint options and copies them straight into `sidebar_action` (`manifest.mjs:165-171`). This would be rejected or would misbehave on submission.

**The Firefox background page is persistent.** `"background": {"scripts": ["background.js"]}` with no `persistent: false` is a persistent MV2 background page. In Chrome MV3 the service worker is killed after roughly 30 seconds idle, which incidentally drops the in-memory decrypted keys held by `KeyVaultService`. That accidental mitigation does not apply on Firefox: decrypted keys stay in memory for the entire browser session. `implement-session-auto-lock` is fixing the absence of a real auto-lock, but the Firefox background lifetime is a manifest problem, not an application one.

**Console output ships.** `wxt.config.ts` sets no `drop_console`, no terser `drop`, and no esbuild `drop`. There are 110 `console` statements across `src/`, and the built `.output/chrome-mv3/background.js` contains 34 `console.log`, 19 `console.warn`, 19 `console.error`, and 3 `console.debug` occurrences.

**The injected script is a stable fingerprint.** `wxt.config.ts:12-17` exposes `injected.js` to `http://*/*` and `https://*/*` with no `use_dynamic_url`. With a static extension id, any page can probe a fixed `chrome-extension://<id>/injected.js` URL and learn that the user runs a Nostr signer.

Two build-output problems sit alongside these. Production source maps are already clean: WXT sets `build.sourcemap = "inline"` only when `command === "serve"` (`builders/vite/index.mjs:50`), and both output directories contain zero `.map` files and no `sourceMappingURL` comment. The published archive is not clean. `pnpm zip:firefox` runs with `zipSources` defaulted to `true` for Firefox, `sourcesRoot` defaulted to the repo root, and only WXT's built-in `excludeSources` list: `**/node_modules`, `**/web-ext.config.ts`, `**/.*`, `**/__tests__/**`, `**/*.+(test|spec).?(c|m)+(j|t)s?(x)`, and `.output/**`. It never reads `.gitignore`. Replaying that exact glob against the working tree yields 2112 files, of which 1796 come from `test-results/` — 122 MB of Playwright output including `chromium-user-data/Default/Local Extension Settings`, the extension's own storage from end-to-end runs. Dotfiles and dot-directories such as `.claude`, `.DS_Store`, and `.wxt` are correctly excluded, both by `**/.*` and because `tinyglobby` does not match dotted path segments by default. The `zip.exclude` list for the extension archive itself defaults to empty, and the extension output ships an unreferenced `icon.png` (644 KB) and `icon.svg` (196 KB) copied from `public/` that no manifest key points at.

Constraints this design works within:

- Four companion changes touch adjacent ground and must not collide. `validate-relay-and-remote-data` owns relay data validation and the avatar URL policy at the application layer. `harden-provider-trust-boundary` owns the injection mechanics in `content.ts`, including `keepInDom`, and owns the decision about narrowing content-script matches. `remove-key-exfiltration-surface` owns deleting the secret-leaking log at `src/infrastructure/messaging/client.ts:45`. `implement-session-auto-lock` will add the `alarms` permission.
- `npx react-doctor@latest` currently fails to install: pnpm rejects it with `ERR_PNPM_TRUST_DOWNGRADE` on `semver@6.3.1`. `restore-security-test-assurance` owns pinning it locally.
- The relay WebSocket lives in the background context. `src/extension/background.ts:229` constructs `RelayManager`, which constructs `NostrRelayAdapter`, which calls `new WebSocket(this.relayUrl)` at `src/infrastructure/relay/nostr-relay.adapter.ts:77`. In MV3, `content_security_policy.extension_pages` governs the service worker as well as extension pages, so `connect-src` constrains relay connections.

## Goals / Non-Goals

**Goals:**

- Declare an explicit content security policy for extension pages on every build target.
- Produce a valid Firefox manifest with no placeholder values.
- Bound how long decrypted key material can live in the Firefox background context.
- Remove `console` output from production builds without asking application code to guard every call.
- Stop the injected script from being a stable, page-probeable fingerprint.
- Request only the permissions the extension actually calls.
- Ship only files the extension needs, and submit only source a reviewer needs.
- Make every property above assertable by a test that reads real build output.
- Record honestly what stands between this repo and a build a user can verify.

**Non-Goals:**

- No application-layer validation of relay responses or avatar URLs. That is `validate-relay-and-remote-data`.
- No change to `content.ts`, `injected.ts`, or the postMessage bridge. That is `harden-provider-trust-boundary`.
- No auto-lock timer, and no `alarms` permission added here. That is `implement-session-auto-lock`.
- No deletion of individual `console` statements from `src/`. `remove-key-exfiltration-surface` deletes the one that leaks a secret; the rest are removed by the build.
- No release signing, no store submission, no CI publishing pipeline.
- No Safari target work.
- No bundle size reduction beyond dropping unreferenced assets.

## Decisions

### Decision 1: Declare `content_security_policy.extension_pages` in `wxt.config.ts`

Add to the `manifest` block:

```
default-src 'self';
script-src 'self';
object-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: https:;
connect-src 'self' wss: https://nostr.build;
font-src 'self';
frame-src 'none';
base-uri 'none';
form-action 'none'
```

Directive by directive:

- `default-src 'self'` — a closed fallback, so a directive nobody thought of does not silently default to permissive. Everything the extension needs is then opened deliberately below.
- `script-src 'self'` — bundled code only. No `'unsafe-eval'`, no `'unsafe-inline'`, no remote origin. `grep` for `eval(` and `new Function` across `src/` returns nothing, so nothing needs relaxing. WXT's own MV3 default includes `'wasm-unsafe-eval'`; Ostrilo has no WebAssembly, so it is omitted. Three.js renders through WebGL, which CSP does not govern.
- `object-src 'self'` — no plugin content. Both Chrome MV3 and the AMO validator expect this directive to be present and restrictive.
- `style-src 'self' 'unsafe-inline'` — this one is a compromise and worth naming. Tailwind compiles to external stylesheets, which need only `'self'`. But `react-style-singleton@2.2.3`, pulled in through `react-remove-scroll` and therefore through every Radix dialog, calls `document.createElement('style')` at runtime and injects a rule. Without `'unsafe-inline'` in `style-src`, dialogs lose their scroll-lock styling. Injected `<style>` content is not a script execution vector, so the cost is presentational CSS injection only, and there is no untrusted CSS source in the extension pages.
- `img-src 'self' data: https:` — extension pages render relay-supplied avatar URLs from `profile.picture` in `KeySelector.tsx`, `KeySelectorCard.tsx`, and `ProfileSummary.tsx`. Those are arbitrary user-controlled URLs, so `img-src` cannot be enumerated. `https:` is a broad source but it excludes plaintext `http:`, which means a relay cannot cause the extension to make a cleartext request that reveals to a network observer which npub's profile is being viewed. `data:` covers the bundled poster image and QR rendering. `validate-relay-and-remote-data` narrows this further at the application layer by rejecting non-`https` picture URLs before they reach an `<img>`; the manifest directive is the backstop for when that check is bypassed or a new render path is added.
- `connect-src 'self' wss: https://nostr.build` — three real needs. `'self'` because `GLTFLoader` fetches the bundled `assets/ostrilo-*.glb` over XHR, and blocking it silently breaks the 3D logo. `https://nostr.build` because `ImageUploadField.tsx:75` posts to the hardcoded `https://nostr.build/api/v2/upload/files`. And `wss:` for relays, discussed next.
- `font-src 'self'` — `grep` finds no `@font-face`, no `fonts.googleapis.com`, and no `@import url(...)` in `src/`. Fonts are system stacks, so nothing remote is needed and the directive can be closed.
- `frame-src 'none'`, `base-uri 'none'`, `form-action 'none'` — the extension embeds no iframes, needs no `<base>`, and its two `<form>` elements (`ImportKeyForm.tsx:75`, `CreateKeyForm.tsx:59`) submit through React `onSubmit` handlers rather than navigating. Closing all three is free hardening and removes three classes of injection escalation.

**On `wss:` and user-configured relays.** A static `connect-src` cannot enumerate relay hosts. Relays are user data: `DEFAULT_RELAY_URLS` in `src/domain/types.ts:55` is a starting point, `settings.service.ts:13-15` offers preset bundles, and `RelayList.tsx` lets a user type any `wss://` URL. Rewriting the manifest at runtime is not possible. So `wss:` stays a scheme wildcard, and that must be stated plainly rather than dressed up: any WebSocket host the user configures is reachable.

What is still gained is not nothing. A scheme wildcard for `wss:` still forbids plaintext `ws:`, so a relay entry can never be downgraded to an unencrypted socket. It forbids `http:` and, combined with the `https://nostr.build` allowlist, means the only non-relay HTTPS destination the extension may reach is the one upload host — so an injected script or a compromised dependency cannot open an arbitrary HTTPS exfiltration channel from an extension page. And `default-src 'self'` closes every transport CSP covers that is not explicitly listed. The wildcard is confined to one scheme on one directive, and the alternative — generating `connect-src` from stored settings — is not expressible in a static manifest.

**Rationale for putting it in `wxt.config.ts`:** WXT accepts `content_security_policy: { extension_pages: "..." }` and handles both target shapes. For MV2, `convertCspToMv2` (`manifest.mjs:347`) flattens the object to the bare string MV2 expects. For MV3, Chrome and Firefox both take the object form. One declaration, correct output on all three target shapes.

**Alternative considered:** relying on the MV3 platform default. It covers `script-src` and `object-src` and nothing else, leaves `connect-src` and `img-src` wide open, is not written down anywhere in this repo, and disappears entirely on MV2. A signer should not depend on a default it does not declare.

### Decision 2: Fix the Firefox `sidebar_action` block at its source, in the sidepanel HTML

Edit `src/extension/sidepanel/index.html`:

- Replace `<title>Default Side Panel Title</title>` with a real title, `Ostrilo`.
- Delete the `<meta name="manifest.default_icon">`, `<meta name="manifest.open_at_install">`, and `<meta name="manifest.browser_style">` tags, along with the commented `manifest.include` and `manifest.exclude` scaffold lines.

With those tags gone, `defaultSidepanel.options.defaultIcon`, `openAtInstall`, and `browserStyle` are `undefined`, WXT emits no key for them, and `sidebar_action` reduces to a valid `{ default_panel, default_title }`. The side panel inherits the extension `icons` block, which is already correct. `browser_style` is deprecated in the WXT type definitions anyway, and `open_at_install: false` is the platform default and the right behaviour for a signer — a side panel should not force itself open on install.

**Rationale:** the placeholders are entrypoint options, not config, so overriding `sidebar_action` from `wxt.config.ts` would leave the wrong values in the HTML for the next person who reads it. Fixing the source removes the class of bug, not the instance.

**This fix is required regardless of Decision 3.** WXT's sidepanel branch checks `browser === "firefox"` before it checks the manifest version (`manifest.mjs:165`), so Firefox MV3 also gets `sidebar_action`, and would inherit the same placeholders.

**Alternative considered:** setting `sidebar_action` explicitly in `wxt.config.ts` to override the generated block. That hides the defect instead of removing it and adds a second source of truth for the same manifest key.

### Decision 3: Move the Firefox target to MV3

Set `manifestVersion: 3` for the Firefox build. WXT's default is `browser === "firefox" || browser === "safari" ? 2 : 3` (`resolve-config.mjs:45`), so this is an explicit override. Firefox has supported MV3 since version 109.

Security consequences, spelled out both ways.

*Staying on MV2.* The background stays a persistent page. `KeyVaultService`'s decrypted key material lives as long as the browser process. There is no idle eviction, so the window in which a memory-disclosure bug, a crash dump, or a swapped memory page can yield a plaintext Nostr private key is the entire browsing session. `implement-session-auto-lock` will close most of this with an explicit timer, but a persistent page means the only thing bounding key lifetime is application code that has to be correct. MV2 also keeps `web_accessible_resources` as a flat string array, which cannot express `use_dynamic_url` (Decision 5), and keeps `injectScript` on its MV2 path, which `fetch`es the resource and assigns `script.text` — inline injection, subject to the page's own CSP (`utils/inject-script.mjs:19`). MV2 does still have one advantage: Firefox MV2 background pages are the configuration this project has actually tested, and `persistent: false` is available as a cheap partial fix that turns the page into an event page without a full migration.

*Moving to MV3.* WXT generates `background: { type, scripts: [background.js] }` for Firefox MV3 (`manifest.mjs:107-110`) — a non-persistent event page. Idle eviction becomes a platform guarantee on Firefox as it already is on Chrome, so the two targets have the same key-lifetime story and `implement-session-auto-lock` has the same substrate to reason about on both. `injectScript` switches to the `script.src` path, which is less entangled with page CSP. And the CSP from Decision 1 lands as `content_security_policy.extension_pages` on both targets rather than an MV2 string with different accepted source expressions, which removes a per-browser divergence from the manifest assertion test.

The recommendation is MV3, with `persistent: false` on MV2 as the documented fallback if MV3 migration surfaces a blocker during implementation. The migration cost is real and is captured in Migration Plan and in Risks.

**Alternative considered:** MV2 with `persistent: false` only. This does bound key lifetime and is a one-line change, so it is the right fallback. It does not unify the CSP shape, does not enable `use_dynamic_url`, does not fix the MV2 inline-injection path, and leaves a second manifest version to maintain indefinitely while Mozilla moves toward MV3.

### Decision 4: This change owns the production console-drop setting; `remove-key-exfiltration-surface` owns the source deletion

Stated explicitly so the two changes do not conflict:

- **`harden-manifest-and-build` (this change) owns** the Vite/esbuild `drop` configuration in `wxt.config.ts`. It is the only change that may add, move, or reword that setting. It also owns the test that asserts no `console` call survives in production output.
- **`remove-key-exfiltration-surface` owns** deleting the specific secret-leaking `console` statement at `src/infrastructure/messaging/client.ts:45`, and any other individual log statement whose *content* is the problem. That change should not add the build setting; if its proposal currently does, this ownership split supersedes it.

The split follows the nature of each defect. A log that prints a private key is a source bug and must be deleted from source: stripping it at build time would still leave it live in every developer's dev build, where the key is just as real. A build that ships 34 `console.log` calls is a build configuration bug, and fixing it in one place is more durable than 110 code review catches.

Implementation is an esbuild `drop` in the existing `vite: () => ({ ... })` factory, applied only for production. The factory already receives WXT's config env, so the condition is available. Because WXT sets `build.minify` to `false` only in serve mode (`builders/vite/index.mjs:49`), production builds already run esbuild, and `drop: ["console", "debugger"]` costs nothing extra.

**Alternative considered:** a `terser` pass with `compress.drop_console`. That would add a dependency and a slower minify step to remove statements esbuild already removes.

**Alternative considered:** a lint rule banning `console` in `src/`. Useful complementary hygiene, and it belongs to `restore-security-test-assurance` if anywhere, but a lint rule does not protect against a dependency that logs.

### Decision 5: Add `use_dynamic_url: true` to the injected script's web-accessible resource

```ts
web_accessible_resources: [
  {
    resources: ["injected.js"],
    matches: ["https://*/*"],
    use_dynamic_url: true,
  },
],
```

The trade-off is exactly the one to expect: it defeats static fingerprinting, and the resource URL is no longer stable. With `use_dynamic_url`, Chrome serves the resource under a per-session GUID rather than the extension id, so a page can no longer probe a fixed URL to detect Ostrilo. The cost is that anything holding a hardcoded resource URL breaks.

**Nothing here holds one.** `content.ts:43` calls WXT's `injectScript("/injected.js", { keepInDom: true })`, and `injectScript` resolves the path through `browser.runtime.getURL(path)` (`utils/inject-script.mjs:16`). `runtime.getURL` returns the dynamic URL when `use_dynamic_url` is set, so the injection continues to resolve. This should still be smoke-tested on a real page, because a silent injection failure means `window.nostr` never appears and the failure mode is a signer that simply is not there.

On Firefox this directive is less load-bearing: Firefox already assigns each installation a random UUID for its `moz-extension://` origin, so the resource URL is not stable across installs regardless. On MV2 the directive cannot be expressed at all — `convertWebAccessibleResourcesToMv2` (`manifest.mjs:331`) flattens each object to its `resources` strings and discards everything else. So `use_dynamic_url` is asserted on the Chrome manifest only.

The `matches` list shown above drops `http://*/*`. That is not this change's decision to make — `harden-provider-trust-boundary` owns whether the provider is offered to plaintext origins — but the web-accessible resource `matches` and the content-script `matches` must agree, so this change adopts whatever that change concludes and asserts the result. See Decision 7.

**Alternative considered:** keeping the static URL and accepting the fingerprint. Extension fingerprinting is a well-understood technique, and for a Nostr signer the leaked bit is not "runs an extension" but "holds Nostr keys", which is a meaningful targeting signal. The mitigation costs one manifest field.

### Decision 6: Least-privilege permission review of the whole set

Current: `permissions: ["storage", "sidePanel", "windows"]` in `wxt.config.ts:12`, appearing verbatim in both manifests.

- **`storage` — keep.** Required. `chrome.storage.local` holds the encrypted vault, and `browser.storage.sync` is read for the `isDocked` flag in `background.ts:355`.
- **`windows` — keep.** Genuinely used, in six places. `background.ts:167` creates the approval popup window, `:151` focuses an existing one, `:197` closes it, `:273` listens on `windows.onRemoved`, `nostr-rpc.ts:438` creates a window, and `useSidePanelDock.ts:52` calls `windows.getCurrent()`.
- **`sidePanel` — remove the explicit entry, but the API is used.** This needed investigating rather than assuming, and the answer is not "unused". `background.ts:357` reads `(browser as any).sidePanel` and calls `setPanelBehavior` and `setOptions`; `useSidePanelDock.ts:16-70` calls `open`, `setOptions`, and `setPanelBehavior`; and Chrome's `chrome.sidePanel` API does require the permission. So Chrome must keep it. What should change is where it comes from. WXT already calls `addPermission(manifest, "sidePanel")` for any MV3 non-Firefox build that has a sidepanel entrypoint (`manifest.mjs:172-173`), so the explicit entry is redundant on Chrome — and it is the reason `"sidePanel"` leaks into the Firefox manifest, where it is not a valid permission name and Firefox will warn on it. Removing it from `wxt.config.ts` yields the correct set on both targets automatically: Chrome keeps it because WXT re-adds it, Firefox drops it because WXT's Firefox branch sets `sidebar_action` without a permission.
- **`alarms` — arriving, not added here.** `implement-session-auto-lock` needs it for the idle timer. It is listed in the reviewed permission allowlist that the manifest assertion test checks (Decision 7) so the two changes compose rather than fighting over the array, but this change does not add it.
- **Host permissions — none, and none should appear.** Both manifests declare no `host_permissions`. They should stay that way. The content script's own `matches` grant it what it needs, and WXT only injects host permissions in serve mode (`manifest.mjs:177-181`).

Resulting reviewed allowlist: `storage`, `windows` on every target; `sidePanel` additionally on Chrome; `alarms` once `implement-session-auto-lock` lands. Anything else fails the assertion.

**Alternative considered:** moving `sidePanel` to `optional_permissions` and requesting it at runtime. Least privilege in the strict sense, since only users who dock the panel would grant it. It also adds a permission prompt to a UI preference toggle and a new failure mode when the grant is declined, for a permission that carries no data access. Not worth it now; recorded as an open question.

### Decision 7: The content-script match list is asserted here, decided elsewhere

Both manifests declare `content_scripts: [{ matches: ["http://*/*", "https://*/*"], run_at: "document_start", js: ["content-scripts/content.js"] }]`, generated from `defineContentScript({ matches: [...] })` at `src/extension/content.ts:35`.

`harden-provider-trust-boundary` owns the security decision about whether the NIP-07 provider should be offered to plaintext `http://` origins. This change does not make that call. What it does is make sure the outcome is asserted somewhere: the manifest assertion test records the expected match list as a literal and compares it against both generated manifests, and the same list is applied to the `web_accessible_resources` entry so the two cannot drift. If `harden-provider-trust-boundary` lands first, this change adopts its list. If this change lands first, it records the current list and `harden-provider-trust-boundary` updates the literal as part of its own work — which is the point, because then narrowing the injection surface cannot be done without a deliberate edit to the assertion.

**Rationale:** the fix and the guarantee belong in different places. A security decision about injection scope belongs with the injection code. A guarantee that the shipped manifest matches the decision belongs with the build.

### Decision 8: Build output hygiene — explicit allowlists, not defaults

Three separate concerns, all currently governed by tool defaults.

**Source maps.** Already correct, and should be locked in. WXT sets `build.sourcemap` only in serve mode, both output directories contain zero `.map` files, and no output JavaScript file carries a `sourceMappingURL` comment. The action is an assertion, not a config change — plus `zip.exclude: ["**/*.map"]` as belt-and-braces so a future `sourcemap: true` for local debugging cannot ship one by accident.

**The extension archive.** `zip.exclude` defaults to `[]`. Set it to drop `**/*.map` and the two unreferenced root assets. `.output/chrome-mv3/icon.png` (644 KB) and `icon.svg` (196 KB) are copied wholesale from `public/`, and no manifest key references either — the `icons` block points at `icons/16.png` through `icons/128.png`, which `@wxt-dev/auto-icons` generates. That is 840 KB of the 3.2 MB output, shipped to every user for nothing. The cleaner fix is to move the two source files out of `public/` so they are not copied at all, since `Logo.tsx:4` imports `@/assets/icon.png` rather than the public copy; `zip.exclude` is the fallback if `@wxt-dev/auto-icons` turns out to need them in `public/`.

**The sources archive.** This is the one that matters, because it is what gets uploaded to Mozilla. Set `zip.excludeSources` explicitly rather than relying on WXT's five built-in patterns, which never read `.gitignore`. At minimum: `test-results/**`, `playwright-report/**`, `coverage/**`, `docs/**`, `openspec/**`, `stats.html`, `stats-*.json`, `**/*.bak`, `logs/**`, `**/*.log`. The measured effect of the first entry alone is removing 1796 of 2112 files and roughly 122 MB, including `chromium-user-data/Default/Local Extension Settings` directories that hold the extension's own storage from end-to-end runs.

Prefer the inverse where WXT allows it. `zip.includeSources` overrides `excludeSources`, so the more defensible configuration is an allowlist of what a reviewer needs to rebuild — `src/**`, `public/**`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `wxt.config.ts`, `tsconfig.json`, `components.json`, `LICENSE`, `README.md` — with `excludeSources` as a second line of defence. That way a new top-level directory in the repo is excluded by default instead of shipped by default, which is the safer failure mode for an archive nobody re-inspects before every submission.

**Rationale:** both defaults fail open. WXT's `excludeSources` enumerates what to omit, so anything new is included; `zip.exclude` is empty, so everything in the output ships. For an artifact that goes to a store reviewer and then to users, the default should be exclusion.

**Alternative considered:** setting `zip.sourcesRoot` to `src/` to sidestep the root-level noise. It would exclude `package.json`, the lockfile, and `wxt.config.ts` — exactly the files a reviewer needs to reproduce the build — so it trades one failure for a worse one.

### Decision 9: Structural centrepiece — a test that asserts on the generated manifests

Every decision above is a property of build output, and build output is not currently asserted by anything. That is why the placeholder `sidebar_action` survived: no test reads `.output/*/manifest.json`. Adding one is the change that keeps the rest from regressing.

Shape:

- A Vitest suite, `tests/security/manifest-assertions.test.ts`, that reads `.output/chrome-mv3/manifest.json` and the Firefox output manifest as JSON.
- Per target, assert: the CSP string contains each required directive and none of the forbidden sources; `permissions` equals the reviewed allowlist for that target; the `injected.js` web-accessible resource entry has the expected `matches` and, on Chrome, `use_dynamic_url: true`; the provider content script has the expected `matches` and `run_at`; `background` is a service worker or a non-persistent page; and no manifest value anywhere contains a placeholder string.
- The placeholder check is a recursive walk over the parsed manifest testing every string leaf against `true|false`, `Default Side Panel Title`, `/icon-16.png`, and `...`. That is what would have caught the Firefox defect, and it catches the next scaffold placeholder too, whatever key it lands in.
- Skip with a clear message when the output directory is absent, so `pnpm test` on a fresh clone does not fail confusingly, but fail loudly when a manifest exists and is wrong. The suite is meaningful only after `pnpm run build` and `pnpm run build:firefox`, which is why the Verification group in `tasks.md` orders them before it.

The spec scenarios in `specs/extension-manifest-policy/spec.md` and `specs/build-output-integrity/spec.md` are written to map onto these assertions one for one, so the specs are checkable against build output rather than against intent.

**Alternative considered:** asserting on `wxt.config.ts` instead. Cheaper and wrong. The whole class of defect here is the gap between what the config says and what WXT generates — the placeholder `sidebar_action` is nowhere in the config, and the `sidePanel` permission on Chrome is added by WXT rather than by the config. Only the generated file is the truth.

**Alternative considered:** a Playwright end-to-end check that loads the built extension and exercises pages under the real CSP. Higher fidelity for catching CSP breakage, and worth having eventually, but slow, and it does not cover the archive contents or the permission set. The manifest assertion is the cheap high-coverage layer; manual smoke of the four extension pages covers runtime CSP breakage for now.

### Decision 10: Verifiable builds — state the gap, fix what is cheap

For a signer, a user should be able to check that the published extension matches this source. Today they cannot, and it is worth being precise about why rather than claiming more than is true.

What already helps: `pnpm-lock.yaml` is committed, `packageManager` pins `pnpm@11.5.2`, dependency versions resolve deterministically, and the Firefox submission already includes a sources archive, so a reviewer at least has the source.

What blocks a byte-identical rebuild:

1. No pinned Node version. `openspec/project.md` says "Node.js 24.x in current development environment", which is a description, not a constraint. A `.nvmrc` or a `packageManager`-adjacent `engines` field costs nothing.
2. No documented build procedure. `README.md` does not state the commands, versions, and environment that produce a published artifact.
3. No published digests. Nothing records the hash of what was uploaded, so there is nothing to compare a local rebuild against.
4. Store re-signing. Both Chrome Web Store and AMO re-sign uploads, so the installed artifact is never byte-identical to the uploaded one. Comparison has to be against the uploaded archive, or per-file against the unpacked install.
5. Unverified bundler determinism. Vite and Rollup output for a fixed input and fixed dependency tree is expected to be stable, but nobody has run the build twice on two machines and diffed it. Until someone has, it is an assumption.

This change fixes items 1 through 3 — pin Node, document the procedure, publish digests of the release artifacts — and records 4 and 5 as future work with the reason. A reproducible-build CI job that builds twice and diffs is the natural next step and is out of scope here.

**Rationale:** partial verifiability that is honestly labelled is more useful than a reproducibility claim that does not survive checking. Users of a signer are exactly the audience that will check.

**Alternative considered:** deferring the whole topic until a release pipeline exists. The three cheap items are cheap now and get harder to retrofit once releases have shipped without them.

## Risks / Trade-offs

- [Risk] A too-strict CSP breaks the 3D model loader or fonts at runtime with no visible error. This is the most likely way this change ships a regression. `GLTFLoader` fetches the bundled `.glb` over XHR, which `connect-src` governs; if `'self'` were omitted, the logo would silently fail to render with only a console message — and Decision 4 removes console output from production, so it would be silent in the shipped build. Radix dialogs depend on runtime `<style>` injection, which fails as missing scroll-lock styling rather than an error. -> Mitigation: `connect-src` includes `'self'` and `style-src` includes `'unsafe-inline'` by deliberate decision, both documented above with the reason. Manual smoke of popup, options, side panel, and the approval window is a required Verification task, with the browser console open and the 3D logo, avatar images, a Radix dialog, and profile image upload each exercised. A dev build retains console output, so CSP violations are visible there.
- [Risk] `form-action 'none'` blocks a form submission path that turns out to be real. Both `<form>` elements use React `onSubmit` and never navigate, so the directive should not fire. -> Mitigation: exercise key import and key creation during the manual smoke; if either breaks, relax to `form-action 'self'`, which is still meaningful hardening.
- [Risk] `use_dynamic_url` breaks provider injection and `window.nostr` silently never appears. -> Mitigation: `injectScript` resolves through `runtime.getURL`, which is dynamic-URL aware, so this is expected to work — but "expected to work" is not verification. Load a real page and assert `window.nostr` exists as part of the manual smoke.
- [Risk] Store-review friction from permission changes. Removing `sidePanel` from the config could, if WXT's automatic addition were to change behaviour, remove it from the Chrome manifest and break the docked side panel. Permission changes can also trigger re-review or a user-facing permission prompt on update. -> Mitigation: the manifest assertion test asserts `sidePanel` is present on Chrome and absent on Firefox, so a regression fails the test rather than the store review. The net Chrome permission set is unchanged, so no new user prompt is expected.
- [Risk] Firefox MV3 migration cost. The output directory changes from `.output/firefox-mv2` to `.output/firefox-mv3`, breaking any doc, fixture, or CI step that hardcodes it. A non-persistent background context can expose module-scope state in `background.ts` that was implicitly surviving for the session — `approvalWindowId` and `approvalWindowOperation` are the candidates. Firefox MV3 also has its own history of API gaps relative to Chrome MV3. -> Mitigation: Chrome already imposes the same suspension constraint, so any such bug is already latent rather than newly introduced; the manifest assertion test covers the new output path; and MV2 with `persistent: false` is the documented fallback if a blocker appears, which preserves the key-lifetime benefit at lower cost.
- [Risk] Dropping `console` removes diagnostics users could otherwise send with a bug report. -> Mitigation: dev builds keep console output, and the activity log already provides a user-visible record of signing decisions, which is the information a bug report about a signer actually needs.
- [Risk] `img-src https:` and `connect-src wss:` remain broad, so this change does not eliminate remote-data risk. -> Mitigation: stated plainly rather than overclaimed. `validate-relay-and-remote-data` owns the application-layer narrowing; the manifest directives are the backstop, and they still exclude every plaintext scheme.
- [Risk] An `includeSources` allowlist omits a file a Mozilla reviewer needs, and the submission is rejected. -> Mitigation: extract the produced sources archive and confirm a clean `pnpm install && pnpm run build:firefox` succeeds from its contents before submission. That is a Verification task.
- [Risk] The manifest assertion test skips silently on a fresh clone with no `.output/`, giving false confidence. -> Mitigation: the skip carries an explicit message naming the build commands, and the Verification group orders both builds before the test run.

## Migration Plan

1. Fix `src/extension/sidepanel/index.html` first. It is independent of everything else, it is the one outright broken output, and it is required whether or not Firefox moves to MV3.
2. Add the CSP, `use_dynamic_url`, and the revised `permissions` array to `wxt.config.ts`. Build both targets and read both manifests before running any test, to confirm WXT emits the shapes Decision 1 expects — object form on MV3, flattened string on MV2.
3. Add the esbuild `drop` setting, production only. Confirm `console` is gone from `.output/chrome-mv3/background.js` and still present in a dev build.
4. Add the manifest assertion test against the current, still-MV2 Firefox output. Getting it green before the MV3 move means the migration has a regression check rather than needing one written afterwards.
5. Move Firefox to `manifestVersion: 3`. Update the assertion's expected background shape and output path, and grep for every hardcoded `.output/firefox-mv2` reference in docs, fixtures, and CI.
6. Add the `zip` configuration. Produce both archives, list their contents, and rebuild from the extracted sources archive.
7. Pin Node, document the build procedure, and record the reproducibility gap.
8. Update `openspec/project.md`, which currently states "Minimal manifest permissions: only `storage` and `sidePanel`" and "Firefox Manifest V2" — both inaccurate after this change, and the first one already inaccurate today because `windows` is requested.

Rollback is per-decision and cheap. Each item is a config or manifest edit with no data migration and no stored-state change. If the CSP breaks a page, relax the offending directive and keep the rest. If Firefox MV3 blocks, revert to `manifestVersion: 2` with `persistent: false` and keep every other item. The manifest assertion test is the thing to keep in all cases, because it is what makes a partial rollback visible instead of silent.

## Open Questions

- Should `connect-src` list the default relay hosts explicitly in addition to `wss:`, as documentation of intent, accepting that the wildcard makes it non-binding?
- Should `sidePanel` become an optional permission requested when the user first docks the panel, or does the added prompt cost more than the least-privilege gain for a permission with no data access?
- Should `img-src` drop `https:` entirely and require avatars to be proxied or cached through the extension, once `validate-relay-and-remote-data` has landed its URL policy?
- Does `@wxt-dev/auto-icons` require `public/icon.png` and `public/icon.svg` to remain in place, or can they move to `src/assets/` so they are never copied into the output?
- Should the sources archive use an `includeSources` allowlist, per the preference in Decision 8, or is an expanded `excludeSources` list less likely to break a Mozilla review?
- Should a reproducible-build CI job that builds twice and diffs the output be a follow-up change, and does it belong with `restore-security-test-assurance`?
