# Interop vectors

Known-answer vectors for Ostrilo's signing path, vendored as data rather than
transcribed into test source.

These exist because a test that signs with Ostrilo and then verifies with
Ostrilo passes just as happily for a wrong-but-consistent implementation. A
vector produced somewhere else does not.

| File | Official? | Consumed by |
|------|-----------|-------------|
| `bip340-schnorr.csv` | Yes - the authoritative BIP-340 vector file, vendored verbatim | `tests/security/bip340-vectors.test.ts` |
| `nip01-events.json` | **No. NIP-01 publishes no official vector file** | `tests/security/nip01-vectors.test.ts` |
| `provenance.json` | - | `load.ts` |
| `load.ts` | - | both suites |

Both suites are hermetic. The files on disk are the only input; no test reaches
the network.

## What each file actually claims

### `bip340-schnorr.csv` - official

The BIP-340 test vectors from `bitcoin/bips`, byte for byte. Nineteen vectors,
indices 0-18: nine expected-valid and ten expected-invalid, each invalid one
carrying upstream's own comment explaining why it must fail. The file retains
its upstream CRLF line endings, which is why `.gitattributes` in this directory
marks it `-text`.

This is a genuine authority. When a vector says a signature is invalid, that is
the Bitcoin specification speaking, not this repository.

### `nip01-events.json` - **not** official

**NIP-01 publishes no official test-vector file.** Nothing in this directory
should ever be described as one, and the file itself opens with that statement.

What it holds instead is fourteen *cross-implementation* known-answer vectors.
Every event was produced and signed by a third-party Nostr implementation, and
every event was published or served by at least one **named** external
implementation of NIP-01. Nothing here was generated by Ostrilo, so reproducing
an id or verifying a signature against these events is an interoperability
check, not a round trip.

Two kinds of attestation are recorded, per vector, under
`provenance.attestations`:

- **Published test fixture.** Three vectors are events that
  [`go-nostr`](https://github.com/nbd-wtf/go-nostr) ships in `event_test.go`
  with the id and signature written out. An independent Go implementation
  asserts those exact answers in its own suite.
- **Served by a public relay.** The rest were retrieved live from public relays
  on 2026-09-13 and then queried back by id across several relays running
  *different* server implementations - strfry (C++), nostr-rs-relay (Rust),
  memlay (Rust), NFDB (Go), haven (Go, khatru/go-nostr), wot-relay (Go) and
  nostr.wine. A vector is only
  recorded as attested by a relay when that relay returned the event
  byte-identical. Relays validate `id` and `sig` on ingest, so an event a relay
  accepted and re-served is an event that implementation agreed with.

Where an event declares a `client` tag, the naming client is recorded too - and
labelled as self-declared, because it is.

Honest counts, which the tests assert and do not round up:

- 12 of 14 vectors carry **two or more** distinct named implementations. Seven
  distinct relay implementations appear across the set: strfry (C++),
  nostr-rs-relay (Rust), memlay (Rust), NFDB (Go), haven (Go, khatru/go-nostr),
  wot-relay (Go) and nostr.wine.
- 2 carry exactly **one**: `kind-3-contacts-json-content` and
  `kind-1-hello-world-secret-key-one`, both from the go-nostr fixture only. No
  relay queried still holds either event - they date from 2022 and 2023. They
  are kept because each covers a serialization shape nothing else here covers,
  and their thinner provenance is recorded rather than hidden.

Every event was independently checked at assembly time - id recomputed from the
serialized fields, signature verified against the pubkey - using
`@noble/curves` directly rather than Ostrilo's code, so the selection was not
circular.

## Drift detection

`load.ts` re-hashes each file at load time and compares against the SHA-256 in
`provenance.json`. A mismatch throws with both hashes and fails the suite. A
vector file that quietly changed is a known-answer test that no longer answers
anything, so this is deliberately loud.

## Refreshing a vector file

1. **Retrieve the new bytes.** Write them straight to the file; do not
   hand-edit, reformat, re-indent, or convert line endings.

   ```sh
   curl -sS -o tests/vectors/bip340-schnorr.csv \
     https://raw.githubusercontent.com/bitcoin/bips/master/bip-0340/test-vectors.csv
   ```

2. **Re-record the checksum.**

   ```sh
   shasum -a 256 tests/vectors/bip340-schnorr.csv
   ```

   Put the hash in the file's `sha256` field in `provenance.json`, and update
   `retrieved` to today's date, `bytes`, and `vector_count` if the count moved.
   For an upstream file, also refresh `upstream_last_commit`:

   ```sh
   curl -sS "https://api.github.com/repos/bitcoin/bips/commits?path=bip-0340/test-vectors.csv&per_page=1"
   ```

3. **Run the suites.**

   ```sh
   pnpm run test:security
   ```

   A checksum mismatch means step 2 was skipped. A vector-count mismatch means
   `vector_count` in `provenance.json` needs updating. A *failing vector* after
   a clean refresh is a real finding: investigate Ostrilo before touching the
   expectation.

4. **Review the diff.** A vendored vector file is executable trust. Read what
   changed before committing, the same as any dependency bump.

## Independent verification tool

`verify-events.mjs` recomputes every event id and verifies every signature in a
vector file using `@noble` directly, **not** Ostrilo's own crypto:

```bash
node tests/vectors/verify-events.mjs tests/vectors/nip01-events.json
```

It prints one line per event and exits non-zero if any id or signature fails, so
it cannot silently pass in a pipeline.

Use it whenever you add or refresh a NIP-01 vector. Selecting vectors with the
same code they are meant to test would be circular: a wrong-but-self-consistent
implementation would happily bless its own output. Last full run, 2026-09-13:
**14/14 verified**.

Note that it reads the whole file at once, so do not run it against a vector
file that is still being written - a partial read reports a spurious id
mismatch.

## Adding a NIP-01 vector

A new event only belongs here if it comes from outside this repository.

1. Retrieve the event from a public relay or an external implementation's
   published fixtures. Keep the relay URL and its NIP-11 `software`/`version`:

   ```sh
   curl -sS -H "Accept: application/nostr+json" https://nos.lol
   ```

2. Confirm it independently. Query the same id from at least one relay running
   a *different* implementation and check the event comes back byte-identical.
   Two relays running strfry are one implementation, not two.

3. Verify the event before trusting it: recompute the id from
   `[0, pubkey, created_at, kind, tags, content]` and verify the signature with
   `@noble/curves` directly - not with Ostrilo's code, or the check is circular.

4. Append the vector with a filled-in `provenance.attestations` list and an
   `exercises` note saying what serialization shape it covers that nothing else
   does. Record the true implementation count. If you can only find one
   attesting implementation, say so; do not pad the list with several hosts
   running the same server.

5. Re-record `sha256` and `vector_count` in `provenance.json`, then run
   `pnpm run test:security`.

**Never add an event that Ostrilo generated.** A self-generated event is a
round-trip test, not a cross-implementation vector, and filing one here would
recreate exactly the false assurance these vectors exist to remove. If a
round-trip check is what you want, it belongs in `tests/unit/`, named as such.
